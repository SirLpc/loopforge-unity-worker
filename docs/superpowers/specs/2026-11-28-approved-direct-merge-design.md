# Unity 功能交付在人工验收后直接合入主线

## 目标与范围

小团队在 LoopForge 完成一次人工验收后，由 Windows Unity Worker 将验收的任务分支合入工程池配置的主线。当前目标是 `unity-ai-development-feature`，工程池的主线是 `main`。用户选择让简单冲突自动解决并合入。分支保护、Git 权限、实际检出的版本和 Unity 检查仍决定本次交付能否成功。

当前发布版的尾部是「测试验证 → 人工验收 → 发起 MR → 交付汇总」。Worker 在验收前已把通过编译的检查点提交推到任务分支。测试报告声明分支和完整 SHA。接入中继根据当前运行的验收产物和测试证据签发授权，Worker 核对签名和保存的任务状态。新能力落在 Unity Worker 和它的 LoopForge 接入。

## 方案选择

1. 自动解冲突并复验后，由原验收人确认解法。人可以检查冲突改动，每次冲突要再经过一次验收。
2. 自动处理简单冲突，通过复验后直接合入。复杂冲突或验证失败停下来交给人工。用户选择此方案。首版使用可机械检查的 .cs 内容冲突规则，再加独立评审，限制 Agent 在验收后可改动的范围。

直接合入由现有 Worker 作业完成。Worker 持有任务分支、Unity 工程槽位、测试选择和验收证据。LoopForge 脚本负责发起作业、等待结果、展示产物和触发归还。安装器沿用同一个工作流 ID，交付节点改为「合入主线」。Worker、中继和安装器支持启用前的 MR 节点和其已有运行快照。

## 授权与交付顺序

1. 安装器显式启用直接合入。Worker 工程池单独允许该能力，目标取该池固定的基础分支和远端身份。用户输入和 Worker API 调用体不能选仓库或目标分支。旧定义、旧任务和已有 MR 交付授权沿用原方式。
2. 人工验收前，Worker 保留现有检查点、评审和测试。验收文案写明批准后会直接合入，简单冲突通过复验会自动交付。中继根据运行快照、新节点和已验收测试产物签发短时授权。签名绑定交付方式及现有的项目、运行、任务、槽位、测试证据和已验收提交 SHA。Worker 校验任务和池已选择同一交付方式，且远端任务分支仍指向该 SHA。验收后出现不同提交时，停止并要求重新验证和验收。
3. Worker 获取最新远端目标 SHA，在已租用的 Unity 槽位构建候选版本，保留任务分支及原测试证据。候选保留主线历史和已验收提交的祖先关系。已验收提交已在远端主线历史时，记录远端确认的已合入状态，不生成空合并。如果候选树等于原测试树，复用绑定到这一树的编译和测试结果。候选树改变时，在候选上重新编译并运行方案批准的 EditMode 和适用的 PlayMode 用例。解过冲突的候选始终重跑这些检查和独立评审。候选校验使用独立结果，保留原评审和测试报告。
4. 检查执行前后核验候选树，避免 Unity 导入或并发进程改动已测内容。推送前再核对远端身份和任务分支。推送只允许把验证时的目标 SHA 快进到同一个候选 SHA。远端目标前进时丢弃旧候选及其验证结果，从新目标再尝试一次。主线持续前进、被重写或已删除，工作分支发生变化，分支保护拒绝或凭证失效时，记录原因并停下来。验收的源 SHA 全程固定。Agent 不持有交付凭证，最终推送由 Worker 执行。

## 简单冲突的判定

- 所有未合并路径都必须是 Unity 工程里的已有、普通 `.cs` 文本源文件，祖先、主线、任务分支三个版本都存在且 Git 文件模式相同。仅接受双方修改同一文件内容的冲突。重命名、添加或删除冲突、二进制、LFS 指针、符号链接、子模块以及 Unity 场景、Prefab、`.meta`、设置和包锁文件冲突交给人工。一份候选混有其他类型的冲突时整份候选暂停。
- 每份候选最多让 Agent 解一次。Agent 可以读取冲突上下文，交付验证只接受原冲突文件中的解法。Worker 拒绝未解项、残留标记、额外文件改动和偏离自动合并结果的非冲突改动。独立评审检查解法对双方改动的保留情况，Worker 在同一个候选上完成 Unity 编译和选定测试。
- 解法超出范围、评审没通过或测试失败时暂停，展示冲突文件、失败阶段和报告。原运行保留阻塞记录、任务分支和诊断证据。同一运行的交付重试用于恢复许可证、网络等基础设施故障，或核对已尝试推送的结果。需要人工改动时，操作员可以按现有 Git 流程接手，或从最新主线启动新 LOOP，重新实现、评审、测试和验收。

## 结果、重试与归还

- 推送前持久化验收标识、原任务 SHA、目标基线和候选 SHA 及验证结果。用现有作业受理和请求 ID 机制防止重复执行。推送响应中断或 Worker 重启后先查远端。远端已包含已记录的候选时补记成功，仍是预期目标时可重试同一候选。远端变化时按前述规则重新构建，远端不可核验时等待人工或下一次重试。
- 合入节点产出 `merge-report.md` 和 `unity-delivery.json`。报告包含任务分支、原验收 SHA、目标分支和基线 SHA、主线合入 SHA、冲突路径、复验结论及远端确认状态。阻塞时在节点展示可操作原因和 Worker 诊断产物引用。交付汇总在远端确认并安全归还槽位后报告成功。失败时按现有恢复和归还流程保留任务现场。
- 运行或交付状态从真实作业及远端确认得出。重试交付汇总只恢复报告或归还操作。该能力不引入平台级交付模式、MR 跟踪改造或其他 LOOP 变更。

## 验证与发布

- 使用临时 Git 远端覆盖已在主线、干净合入、可解与超范围冲突、候选证据变化、Unity 检查失败、权限拒绝、源或目标分支并发变化、推送成功但响应丢失和重启恢复。
- 覆盖 Worker 授权及幂等、旧签名和旧工作流快照兼容、节点和产物契约、安全归还。按本机约定在沙箱外使用 Unity 2022.3.62f3，在隔离验收工程验证合并候选的实际 EditMode 和 PlayMode。
- 先让兼容的 Worker 和中继就绪，再通过安装器预览目标 SOP 的最新 revision，按预览版本更新并验证发布内容。自动化和端到端验收使用隔离远端。正式流程只有对应运行获人工批准后才允许更新正式主线。回退时恢复此前工作流版本，已启动的运行按冻结图继续。

## 实现细节

实现沿用 Worker 的任务记录、工作区快照、Git 传输和 Unity 执行器。候选使用已租赁槽位中的检出，完成后恢复任务分支，再走槽位归还检查。主线推送必须由远端原子比较目标 SHA。Git 的源分支复查和目标分支更新是两个操作，复查后即使有人改动源分支，推送仍使用固定的已验收源 SHA。具体 Git 命令、存储字段、作业名和报表排版由实现计划细化。
