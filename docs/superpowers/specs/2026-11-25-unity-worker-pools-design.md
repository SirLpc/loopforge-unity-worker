# Unity Worker 多目录池设计

## 目标

多个需求 SOP 共用一个 Worker HTTP 入口。每个命名池对应一个受信任的 Git 仓库、基础分支和 Unity 工程配置，池内若干独立常驻检出可并行服务。首发把当前正式项目的两个检出放进同一个池。用户同时提交两条需求 SOP，两单各自开发、编译、测试、审批和交付。再多一单时，启用排队的 SOP 会等待该池释放目录。

当前服务把 `project`、`git_root` 和租约绑定到一个 Worker ID，正式需求 SOP 在方案审批后统一调用它。已审查但尚未提交的内容仍存在于工作区，因此一单从首次分配到安全释放期间持续占用同一目录，包括人工审批、暂停、失败及恢复。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| 单入口 Worker 统一调度多个目录 | 通过一个 SQLite 事务记录任务、Job、队列和租约。现有开发和审批状态机改为使用已分配目录。运行恢复沿用同一组任务与 Job ID。 |
| 每目录一个 Worker，前置路由服务 | 可复用单目录进程模型。路由层和每个进程各有持久状态，需要协调远程接单、断线重试、取消和发布版本。 |

采用第一种。已确认首版支持多个命名池，先启用当前项目的两个目录。服务保持单个 Uvicorn 进程，独立目录的工作并发执行，SQLite 事务仅处理状态，Git、Codex、Unity 和网络调用在事务外运行。LoopForge Go 核心沿用现有脚本节点、凭据和产物交接。

## 配置、隔离与容量

- `worker_id`、`logs`、`codex_exe`、`codex_home` 和服务凭据属于服务。池模式配置 `default_pool`、`legacy_slot` 和 `[pools.<pool_id>]`，池项定义 `git_remote`、预期 `remote_identity`（沿用现有 fetch/push 远端元组的 SHA-256）、`base_branch`、`unity_exe`、`unity_version`、测试范围和 Git 缓存规则。`[[pools.<pool_id>.slots]]` 每项定义全局唯一 `id`、`git_root`、`project` 及默认开启的 `enabled`。所有槽位复用服务顶层 `codex_home` 中的一份登录。每个任务或审查调用启动独立 Codex 会话，按所属 checkout 限制写权限。可选 PR/MR 用该池的适配器和凭据，历史默认池继承原配置。所有池使用同一个受信任的操作范围。`default_pool` 和供旧入口使用的 `legacy_slot` 随状态库固定。持久化池的仓库、分支、相对工程路径和版本，以及槽位的池和真实路径。需替换目录或仓库时排空原槽位并使用新 ID。每池新配置的交付适配器或其他执行配置变更在该池全部未结束任务处理完后生效。
- 复用现有 Windows 项目保留锁，每个 checkout 保留一把，并加一把状态目录保留锁。规范化大小写和路径别名，拒绝重复或祖先重叠的检出、跨目录的 junction 或共享可变项目缓存。每个目录具备自身 `.git`、Unity `Library`、`Temp`、日志和依赖状态。池内仓库身份、Unity 工程相对路径、版本及基础分支配置一致。只接受配置中的命名池和目录，HTTP 请求传 `pool_id`，目录、远端和可执行文件都由 Worker 配置决定。
- 配置结构错误会阻止启动。启动预检发现单个目录缺失、版本、远端、Git 状态或 Editor 锁异常时，只把该目录设为 `unavailable`，已绑定任务仍可查询。操作员修正后在服务重启时复检。真正切分支前再次核对清洁状态和远端身份。分配后若发现工作区异常，保留任务和现场，操作员在原目录处理并释放。其余目录继续接单。
- 每个可用目录可持有一单。服务另设 `max_parallel_unity` 控制全机同时运行的 Unity 工具进程，首发从 1 开始，两个目录可同时跑 Git、Codex 和独立审查。通过双 Editor 实测后可设 2。Unity 启动前记录 Job 的 Editor 使用权，确认进程树退出才释放。进程状态不明或服务重启时保留该记录，按现有人工恢复流程确认停止后释放。使用权占满时，其它目录仍可启动非 Unity 阶段，进入 Unity 阶段后可取消地等待。

## 分配、重试与交付

1. `POST /api/v1/tasks` 可选 `pool_id`，省略走默认池。创建时固定池，校验该池的定向测试范围。原请求 ID 重放取回同一任务，换池或改输入视为冲突。显式和省略默认池等价，签名兼容旧请求。创建本身不占目录。
2. 第一次 `run` 或 `prepare` 获取租约。请求可选 `queue_wait_seconds`，整数范围 1 至 86400。提供时服务返回可查询的 Job 资源，依池内入队顺序分配。满池时显示 `queued`，超时且未分配时结束 Job 并记录 `queue_timeout`，任务仍可显式重试。旧调用省略该字段，容量可用时立即启动，否则维持 `409`。新请求不得越过同池已有队列。
3. SQLite 保持现有全局唯一 `request_id`，并约束每个 `slot_id` 最多一个持有租约的任务，每任务最多一个 `queued` 或 `running` Job。`BEGIN IMMEDIATE` 同时写入任务绑定、租约、Job 状态。进程内启动、取消、关闭和释放协调使用同一把短时间锁。排队取消不启动工具进程或占用目录。运行后取消沿用进程树终止及安全释放流程。线程启动失败只更新该 Job 和任务。
4. 一经分配，任务的 `pool_id` 和 `slot_id` 固定。Git、Codex、Unity 及 PR/MR 均使用该槽位与池的配置。日志和产物继续按任务及 Job ID 存放。审批、提交和推送沿用现有 revision 和 Git 树核对。每单仍独立提交 `ai/task-*` 分支，交付保留基础提交，后续按仓库现有流程合并。
5. `release` 在确认 Unity 关闭、Git 目录干净且没有待恢复进程后释放租约，保留历史槽位标识，唤醒同池队首。启动时继续调度未过期的排队 Job，启动前已标记 `running` 的 Job 转入 `recovery_required`，保留目录绑定。只移除已排空、无绑定作业且无任何进程待确认的槽位。`enabled=false` 暂停新分配，当前持有租约的任务可以完成或恢复。

## 接口与 SOP

- 任务状态、开发产物和交付产物增加 `pool_id`、`slot_id`，未分配时 `slot_id` 为 `null`。Job 查询增加 `queued`。新增鉴权 `GET /api/v1/pools`，返回每池 `queued_count` 和每目录的 `id`、状态、当前 `task_id` 与阶段，状态使用 `idle`、`leased`、`recovery_required`、`unavailable` 或 `draining`。API 只公开标识，运行日志沿用脱敏。
- `/health` 和旧 `/jobs` 继续使用原默认目录及响应格式。`/api/v1/workers` 保留现有单条聚合记录和字段，状态反映默认池。新安装器直接用池列表检查两目录容量与状态。Worker 的普通凭据与人工审批凭据继续分开。
- `worker_client.py` 的 `create/develop` 从受信任执行 SOP 固定参数读取 `--pool`。`develop/run/prepare` 支持 `--queue-wait-seconds`，分开轮询排队和执行时间。产物保留现有 `plan_request_id`、`task_id` 和 `revision`，追加池、目录和基础提交。重连用原 Job ID 查询，包括旧版提交的运行中 Job。过期排队 Job 在明确换 `--attempt` 之前保持终态，避免 SOP 重跑时重新排队。交付和释放由任务 ID 路由，核对已有产物中的池与目录；旧产物字段缺失时沿用原校验。
- 三条现有需求 SOP 仍走同一个执行子 SOP，新版本固定映射到现有项目的命名池。排队上限初定为 18000 秒，执行保留现有 18000 秒预算。节点收到终止信号时请求取消，断线先用已有 ID 重连。Worker 自己执行排队截止时间，即使节点消失也能结束未获目录的 Job。

## 迁移与验收

- 兼容现有单目录 TOML 与环境变量，归一为一个默认池和一个槽位。旧数据库在停服备份后用事务迁移；保留任务、Job、请求签名、产物路径和租约。历史已分配任务映射到原目录，尚未开始的任务留在默认池待分配。正式启用第二个目录后，回退容量时排空第二个目录再禁用它，继续使用升级后的数据库保留新旧任务记录。
- 正式配置的第一目录为现有 `worker-01`，第二目录拟为同一基线的 `worker-02`。D 盘检查时约有 61 GiB 可用，现有检出的 `.git`、`Library` 和资产合计约 30 GiB。开工前重新估算克隆、LFS 和首次导入峰值，预热干净的第二检出，核对版本、授权、LFS 和定向测试。Unity EditMode / PlayMode 在 Windows 沙箱外验证。Worker 源代码与运行目录已有差异，开发基线须保留两处现有修订。
- 发布先升级兼容 Worker 服务，再发布新的执行子 SOP。旧运行可继续读原 Job 与产物。新版安装器从目标池读取允许测试范围，并分别验证两个目录的 Git、Unity、Codex 证据和跨平台产物交接。灰度期间保留现有已发布版本。若降回旧 Worker 二进制，只可在升级后尚无新操作时使用切换前快照。
- 双槽验收同时发起两条需求，观察工作过程确实重叠、各自 `-projectPath`、分支、revision、日志及报告独立，分别完成审批、交付与释放。提交第三条，证明等待该池目录并在释放后从原 Job 接续。再验证隔离第二命名池、排队取消和超时、重复请求、跨槽路径阻断、掉电重启、脏目录隔离及旧单目录兼容。并发 Editor 以 Windows 真实进程、Unity 日志和 XML 为证据。
