# Worker 目录占用与手工释放设计

## 目标

Windows 运维人员通过同一个 PowerShell 入口查看 Worker 目录的任务占用和磁盘用量，手工归还已结束任务持有的槽位，并按需清理空闲槽位的 Unity 缓存。现有单工程与命名池部署均可使用。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| PowerShell 命令与 Worker API | 沿用运维脚本及凭据，Worker 可以在运行中协调清理和槽位分配。 |
| 浏览器管理页与 Worker API | 适合高频查看和点选操作，需要额外的页面和浏览器认证流程。 |
| 本机离线脚本 | 磁盘清理需停服，归还任务槽位仍通过 Worker API。 |

用户选择 PowerShell 命令与 Worker API。脚本负责展示和确认，Worker 拥有槽位状态、配置路径和清理权限。

## 运维入口

新增 `scripts/workspace-maintenance.ps1`，使用现有的 Worker URL、Operator Token 环境变量及可选的 DPAPI 凭据目录。脚本使用四个操作。

- `Status` 为默认操作。列出配置中的池和槽位、租约状态、任务 ID 与当前阶段，以及各槽位和状态目录所在卷的总容量与可用空间。该操作只读状态与卷容量，可以在服务忙碌时使用。
- `Measure -SlotId <id>` 扫描指定 checkout，展示合计和主要分项，包括 `.git`、Unity `Library`、`Temp`、`Obj` 和其余文件。另用 `Measure -State` 查看 Worker 状态目录，包含日志和任务产物。扫描报告逻辑文件字节数，卷容量反映文件系统报告的实际空间。扫描期间目录可能变化。跳过符号链接和 Windows 重解析点，显式报告跳过项和未读完的统计。相同卷的容量可以出现在多行，各行容量不参与求和。
- `Release -TaskId <uuid>` 提交现有任务 `release` 操作并轮询 Job，展示归还成功或具体阻断原因。任务已结束、Unity 已关闭、Git 工作区符合要求和没有待恢复 Editor 进程等检查继续由现有流程处理。归还后槽位可立即参与调度。中断本地等待只停止轮询，操作人员可以通过 Job ID 继续查询。
- `Clean -SlotId <id> -Cache <name>` 显示目标、预计可回收的逻辑字节数及确认提示。候选为 Unity 工程直属的 `Library`、`Temp` 和 `Obj`，每次明确选一个。选择 `Library` 时提示下次打开或运行 Unity 需要重新导入。未确认、目标缓存的扫描不完整或操作条件不满足时结束。操作完成后显示删除结果和卷剩余空间。归还和清理是两个独立操作，若归还后另一个任务先获得槽位，清理会被拒绝。

详细测量按需启动，避免每次打开总览都递归扫描常驻工程。日志和任务产物、SQLite、Git 与 LFS 数据、项目源码和共享 Codex 登录目录均受清理边界保护。首版覆盖指定槽位的上述三种缓存。

## 服务端行为

- 新增 Operator Token 专用的 `GET /api/v1/storage`、`GET /api/v1/storage/slots/{slot_id}`、`GET /api/v1/storage/state` 和 `POST /api/v1/storage/slots/{slot_id}/clean`。读取接口分别提供总览、槽位统计与状态目录统计。清理提交固定缓存名和布尔值 `confirmed=true`，路径从服务配置推导。槽位和缓存 API 只接受配置中的槽位 ID 及固定缓存名。
- 在调度和任务提交使用的同一把锁下核对目标槽位与租约，拒绝已租用、需要恢复、不可用、正在维护或 Worker 正在停止的槽位。已禁用且已排空的槽位可以清理。取得维护占用后释放锁，再执行文件检查与删除。维护期间 `Status` 显示为 `maintenance`。现有池 API 将该槽位显示为 `unavailable`，沿用现有状态值。普通分配、队列和旧 smoke 均避开它，其他槽位可继续工作。优雅重启等待清理结束，清理结束后唤醒调度。
- 删除前重新检查 Unity 锁、checkout 与工程根的真实路径、缓存路径及其中的文件。拒绝根或目标路径异常、任何符号链接和重解析点。只清理 Git 忽略的缓存，拒绝当前索引或 HEAD 中的跟踪文件和子模块、Git 未忽略的本地文件及内嵌 Git 仓库。缓存目录必须是已配置工程的直属子目录。沿用服务专用 checkout 的约束，运行维护时外部 Git 客户端及 Editor 不能并发改写该工作区。
- 每次仅处理一个缓存。确认路径后先把缓存移入同一工程目录中新建的 `.unity-worker-cleanup-` 前缀临时目录，再删除该临时目录，使原缓存路径一次性移除。不存在的缓存返回无需清理。移动之前的失败会释放维护占用。移动之后若删除失败，返回失败和遗留位置，由操作人员检查处理。仍有维护遗留的槽位暂停接单，服务重启时也检查该情况，包含单工程部署。处理遗留目录后通过现有的重启流程复检。服务日志记录清理请求的槽位、缓存和结果。
- 清理调用同步返回，脚本遇到连接中断时提示重新查询状态和预览。保留现有任务 API、凭据规则与 release Job 记录。实现不需要改动 Worker 数据库结构或安装依赖。

## 验收

- 用临时目录验证单工程和多池的总览、checkout 和状态目录统计、缺失目录和部分扫描结果，以及链接外的文件不会计入。
- 验证脚本可使用 Operator Token 查看状态和启动手工操作。测试 Release 在成功及受阻情况下的反馈，现有任务与集成调用继续通过。
- 验证清理只对明确选中的缓存生效。未确认、普通 Worker Token、受跟踪文件、未被 Git 忽略的文件、内嵌 Git 仓库、异常路径、符号链接或重解析点、Unity 锁、已有租约、旧 smoke 恢复标记和停服状态均应拒绝。
- 模拟队列与并发清理，确认只有目标槽位暂停分配，优雅重启等待维护结束。模拟删除失败和重启后检测遗留目录，使用说明写明复检步骤。
- 使用临时 fixture 和模拟工具验证，避免触碰部署中的生产 checkout。若需要真实 Unity 验收，使用专用验证工程，在 Windows 沙箱外执行。

## 实现决定

初版的测量分项、缓存白名单、保护未忽略本地文件和内嵌 Git 仓库、单目标同步清理、只用 Operator Token 访问新接口，以及删除失败时重新复检的方式，由实现侧提出。脚本表格列宽、HTTP 错误体结构与扫描实现细节由实施阶段确定，沿用仓库既有约定。
