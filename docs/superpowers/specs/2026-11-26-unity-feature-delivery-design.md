# Unity 功能交付 SOP 设计

## 目标

将 Unity-AI-Development 的「Unity 功能交付」改成与 LoopForge 体验项目「测试功能sop」相同的八个业务节点。Unity Worker 在需求定型时征用一个配置好的工程槽位。读取、修改、评审、Unity 测试和交付沿用该任务、槽位和基础提交。测试通过后由用户在 LoopForge 做一次人工验收，该次验收授权交付同一份已验证的修改。

改造落在 Worker 的任务模式和 LoopForge 接入。安装器只发布项目现有的功能 SOP。运行使用 LoopForge 创建时保存的工作流快照，Worker 按任务创建时选中的模式执行。

## 选定方案

1. **LoopForge 逐节点调用 Worker。** 每个节点发起对应的 Worker 作业、等待结果并登记证据。画布反映实际执行顺序，便于定位失败和重跑阶段。用户选择了此方案。
2. **Worker 执行组合开发作业。** Worker 依序完成实现、评审和测试并交接各阶段结果。返工和重试以组合作业为单位。

## 节点

| 节点 | 操作及产物 |
| --- | --- |
| 需求定型 | 读当前 LoopForge 需求，创建功能交付任务并取得工程槽位。Worker 在只读会话中定型目标、范围、用户和可验收条件，输出 `requirement.md` 与任务绑定信息。 |
| 方案设计 | Worker 在同一个工程的基础提交上检查代码和 Unity 配置，核对源码位置、实现范围和定向测试夹具。按需运行基线检查，输出 `design.md` 与带摘要的计划。可信脚本在开发开始前验证并冻结该计划。 |
| 开发实现 | 按冻结方案修改工程，运行编译并记录实际修改、编译结果和 Git tree revision，输出 `implementation.md`。 |
| 独立评审 | Worker 用独立会话评审该 revision 的改动与编译证据，输出 `review.md`。通过才能进入测试。 |
| 测试验证 | Worker 在已评审的同一 revision 运行方案选中的 Unity EditMode 和适用的 PlayMode 夹具，校验测试 XML 和实际覆盖，输出 `test-report.md` 与本轮验证记录。 |
| 人工验收 | 在 LoopForge 审阅需求、实现、评审和测试证据。批准授权当前测试版本交付。打回携带意见回到开发实现，在原任务和槽位重做实现、评审和测试。 |
| 发起 MR | Worker 核对验收授权与当前 revision 后提交并正常推送任务分支。配置适配器时创建或复用该源分支到基础分支的 MR/PR。以 `mr-body.md` 记录分支、提交和 MR 状态。 |
| 交付汇总 | 汇总实际通过的验证、未覆盖项、任务分支、提交和 MR 状态，输出 `delivery.md`，记录 Worker 归还槽位的结果。 |

MR 适配器沿用 Worker 工程池配置。当前部署交付分支，MR 标为待创建并附源分支、目标分支和提交。已配置的适配器请求失败时，节点报告失败，保存已推送的分支和提交，并允许同一运行只重试 MR。基础分支取自工程池配置。

## Worker 与 LoopForge 交接

- 功能交付用显式任务模式。扩展现有目录池、规划、阶段执行、Git 和 Unity 代码。旧任务缺省进入原模式。Worker 使用现有任务存储记录各阶段状态。
- LoopForge 节点使用可信脚本。Runner 中继读取平台运行和当前节点状态，核对项目、工作流和容器归属。它根据平台的产物 ID、节点执行次数和摘要核对上游证据。Worker 依据自身保存的任务、槽位、基础提交、方案摘要和修改 revision 决定允许的下个操作。
- 现有测试范围校验决定程序集和夹具的合法性。方案列出所需的 EditMode 夹具及适用 PlayMode 夹具，可指定本次实现将新增的夹具。Worker 校验测试 XML，要求运行所选夹具并取得有效结果。报告列出通过、失败、未运行及未覆盖范围，人工验收据此检查需求。

## 验收授权与返工

- 发起 MR 节点开始执行时，中继核对当前平台批准记录和测试产物的 ID 与摘要，签发短时授权。授权绑定项目、运行、验收次数、任务、槽位、基础提交、已评审及测试的 Git tree revision 和测试作业。签名密钥保存在中继与 Worker，脚本只接收授权。Worker 核验后在同一事务记录 LoopForge 验收并受理提交作业。提交之前再次比较实际 Git 树。
- 授权以 Worker 受理作业为界。新作业需要当前有效授权，运行中的作业用原 Job ID 继续。取消时通过现有 Worker 取消和恢复机制处理已经受理的作业。推送成功后的 MR 重试使用已记录的提交和当前验收授权。验收者沿用原平台批准记录。
- 验收使用 LoopForge 的「打回」动作重置实现及下游节点。Worker 从当前运行的重做次数和反馈开始下一轮，保持任务、槽位、基础提交和冻结方案，作废此前的评审、测试和批准。已有返工上限适用。变更需求范围或测试计划时从需求重新运行。
- 编译、评审或测试失败停在对应步骤，报告 Worker 原因和产物引用。可恢复的基础设施失败重试该阶段，确定需要改代码的失败通过现有运行重试入口从实现开始。相同作业的重连继续已有 Job，明确重试已失败的操作使用新的请求 ID。
- 完成交付后通过 Worker 的安全检查归还槽位。等待 MR 重试、失败、取消和进程退出待确认时保留现场。需要放弃时走 Worker 已有的归档、恢复和释放流程。

## 验证与上线

- 自动核对 SOP 节点、连线、产物名字和唯一人工验收。覆盖租约一致性、阶段顺序、验收打回、同一操作重试、错误签名、旧审批、修改后的 Git 树、测试失败和 MR 降级。保留旧任务路径的回归测试。
- 使用独立 Worker 验收工程和临时 Git 远端，验证从征用到归还的路径及真实 Unity 定向 EditMode 和 PlayMode 结果。Unity 2022.3.62f3 测试按本机约定在沙箱外运行。
- 用 LoopForge 的正常 API 验证画布、产物和唯一验收。上线先启用兼容新旧模式的 Worker 与中继，再发布目标 SOP 的同一 ID，检查项目默认入口及发布版本。以原 SOP revision 回退新建运行，已创建的运行继续按其快照和任务模式执行。
